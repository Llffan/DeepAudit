# 医疗质控系统数据库设计文档

● 按业务流程顺序讲，6 张表实际上对应质控系统的 5 个角色 + 1 张 Flyway 元数据：

---

### 1. qc_rule —— 规则库
**定位**：所有质控规则的定义存这里。每条规则就是一行。

| 字段                   | 含义                                                         |
| :--------------------- | :----------------------------------------------------------- |
| code                   | 规则编码 R001 / R002 / R003...                               |
| name                   | 规则名（用于 UI 展示）                                       |
| dimension              | 4 个质控维度：completeness / logic / standardization / consistency |
| severity               | 处置等级：mandatory（强制）/ deduction（扣分）/ hint（提示） |
| expression             | JSON DSL，规则的可执行逻辑（"主手术编码非空时术者必填"这种） |
| error_message_template | 命中时的提示模板，含 {{字段名}} 占位                         |
| enabled                | 软开关，关掉就不参与检查                                     |
| description_embedding  | 规则描述的向量，用于"用户新建规则时检测是否已存在重复"       |
| deleted_at             | 软删除时间戳                                                 |

**生命周期**：
- 启动时已经有 2 条种子（R001/R002）
- 规则配置页用户增删改 → 写这里
- "已启用规则不可硬删除"，靠 deleted_at 软删

**关联**：每条 check_result 都引用一条 qc_rule.id。

---

### 2. medical_record_main —— 病案主表
**定位**：每条病案首页的主记录，30 个核心字段全在这里。

| 字段块         | 字段                                                         |
| :------------- | :----------------------------------------------------------- |
| 基本信息 (6)   | 病案号、姓名、性别、出生日期、年龄、身份证（脱敏）           |
| 入出院 (7)     | 入院日期、出院日期、住院天数、入院/出院科室、入院途径、离院方式 |
| 诊断 (5)       | 主诊编码/名称、ICD 版本、其他诊断数、病理诊断                |
| 手术 (5)       | 主手术编码/名称、手术日期、术者、麻醉方式                    |
| 费用 (4)       | 总费用、药品费、手术费、医疗服务费                           |
| 元数据 (3+1+1) | 来源医院、PDF 路径、抽取置信度、状态、软删除                 |

**status 字段是状态机**：
`draft`（草稿，刚抽取出来未确认）
  ↓ 用户点"确认提交"
`confirmed`（已确认，等待跑规则检查）
  ↓ 跑完规则
`checked`（已检查）
  ↑ 用户改字段后回到 confirmed 重检

**生命周期**：
- 用户上传 PDF → LLM 抽取 → 创建 status=draft 的记录
- 用户在前端审核/修改字段 → 改 status=confirmed
- 后端跑规则 → 改 status=checked，同时往 check_result 插命中记录

**关联**：被 medical_record_extra、check_result 引用，删除时级联删（ON DELETE CASCADE）。

---

### 3. medical_record_extra —— 病案兜底表（JSONB）
**定位**：30 主字段之外的所有字段都丢这里。

| 字段         | 含义                                    |
| :----------- | :-------------------------------------- |
| record_id    | 关联到 medical_record_main.id（一对一） |
| extra_fields | JSONB，键值对随便放                     |

**为什么单拎出来**：
- 病案首页 HQMS 标准有 168 个字段，主表只精选了 30 个
- 剩下 138 个（联系人地址、医保信息、签字医生、费用 26 类细分等）放这里不丢数据
- 单拆一张表是为了主表查询不被 JSONB 拖慢

**生命周期**：跟 medical_record_main 一对一，主记录建时同时建。

**已知限制**：MVP 的规则 DSL 不能引用 extra_fields 内字段，所以扔进来的字段暂时只能当存档，不参与质控。

---

### 4. check_result —— 质控检查命中记录
**定位**：每条规则在某条病案上命中一次 = 这里一行。

| 字段块   | 字段                                                         |
| :------- | :----------------------------------------------------------- |
| 关联     | record_id → 病案主表，rule_id → 规则表                       |
| 写时快照 | rule_code_snapshot / rule_name_snapshot / rule_severity_snapshot / rule_dimension_snapshot |
| 命中详情 | field_path（哪个字段触发）、field_value_snapshot（当时的字段值）、hit_message（错误消息） |
| LLM 解释 | llm_explanation + llm_explained_at（懒加载缓存）             |
| 用户处置 | status：open（未处理）/ acknowledged（已确认）/ false_positive（误报） |

**为什么有快照字段**：
- 命中后管理员可能改 R001 规则的名字或处置等级
- 改完不应该污染历史记录的展示（"我两个月前看的报告里 R001 显示是'强制'，怎么现在变成'提示'了？"）
- 写时快照规则名称、维度、处置等级，历史就被冻结住

**LLM 解释为什么是缓存而不是实时**：
- 用户在结果列表里只看到一句简短的 hit_message
- 想看详细解释时再点 → 那时才调 LLM 生成长文 → 写到 llm_explanation
- 同一条命中第二次点 → 直接读缓存，不再花钱

**status 字段的价值**：用户标"误报"后，未来可以聚合统计每条规则的误报率，作为规则迭代的依据。

**生命周期**：
- 跑规则时插入
- LLM 解释只在用户首次查看详情时填
- 用户处置时改 status

**关联**：record_id → medical_record_main（级联删），rule_id → qc_rule（不级联，规则只能软删）。

---

### 5. icd_dict —— ICD 编码字典 + 向量
**定位**：国家临床版 ICD-10（疾病）+ ICD-9-CM-3（手术）编码表，带向量。

| 字段           | 含义                         |
| :------------- | :--------------------------- |
| code           | 编码 J42.x00、47.0901 等     |
| name           | 编码对应的疾病/手术名        |
| category       | icd10 或 icd9cm3             |
| version        | 版本，如 "ICD-10 国临版 2.0" |
| name_embedding | 1024 维向量，用于语义检索    |

**为什么要向量列**：
- 用户在规则配置界面输入"阑尾切除术" → 后端把 query 也向量化 → pgvector 余弦相似度找最近的 10 条 → 返回候选编码（含 47.0901 腹腔镜下阑尾切除术）
- 比传统 LIKE 模糊查询好太多 —— "心绞痛" 能命中 "不稳定性心绞痛"，"颈椎病" 能命中 "颈椎间盘突出"

**生命周期**：
- V1 启动后是空的
- V2 迁移（待做）灌入 1000 条高频编码 + 预计算的向量
- 之后基本只读，年度国临版字典升级时再更新

**关联**：在数据库里没有外键，只是被 medical_record_main.main_diagnosis_code 等字段逻辑引用（前端校验/补全时用）。

---

### 6. flyway_schema_history —— Flyway 自管表
**定位**：Flyway 的"已跑过哪些迁移"记账本，纯运维元数据，业务不要碰。

| 字段           | 含义                                            |
| :------------- | :---------------------------------------------- |
| version        | 迁移版本号 1, 2, 3 ...                          |
| description    | 文件名里的描述部分（init schema, seed icd ...） |
| script         | 文件名                                          |
| checksum       | 文件 MD5，下次启动时拿来比对，改过就拒绝启动    |
| installed_on   | 跑的时间                                        |
| success        | 成功还是失败                                    |
| execution_time | 耗时毫秒                                        |

**机制**：每次启动 backend，Flyway 读这张表 → 比对 classpath 上的 V*.sql → 跑没跑过的。

---

### 总结
**5 张业务表 + 1 张元数据 = 一个最小完整的质控系统**

**如果用一句话串起来**：
> 用户在 `qc_rule` 里配规则，上传的病案进 `medical_record_main`（+ `medical_record_extra`），跑规则后命中结果落到 `check_result`，规则配置 / 编码自动补全靠 `icd_dict` 做语义检索，所有 schema 演进由 `flyway_schema_history` 守门。

**查询实际字段类型指令**：
`docker compose exec -T db psql -U deepaudit -d deepaudit -c "\d <表名>"`
