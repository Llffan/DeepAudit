# 算子体系全景梳理与动态化方案深度解析

## 1. 三层算子分类

按“是否持久化”和“扩展机制”分为以下三层：

### 层 A：内置纯逻辑算子（17 个）

- **算子名**：`and` / `or` / `not` / `notNull` / `isNull` / `eq` / `ne` / `gt` / `gte` / `lt` / `lte` / `dateBefore` / `dateAfter` / `dateDiffDays` / `ageYears`
- **实现位置**：`RuleEvaluator.evalBool` + `evalValue` 硬编码 `switch`
- **持久化**：❌ Java 代码
- **扩展方式**：修改代码 → 修改白名单 → 增加测试（三处同步）

### 层 B：内置 DB-backed 算子（1 个）

- **算子名**：`icdCodeExists`
- **实现位置**：`RuleEvaluator.evalBool` + `IcdDictCache` 内存索引
- **持久化**：❌ 算子本身硬编码；✅ 依赖的字典数据持久化在 `icd_dict` 表
- **扩展方式**：修改代码 + 灌入字典数据

### 层 C：自定义算子模板（动态）

- **算子名**：`custom`（分发器）+ DB 表中定义的所有算子模板
- **实现位置**：`RuleEvaluator.evalBool` 的 `case "custom"` + `CustomOperatorRegistry` + `qc_operator_template` 表
- **持久化**：✅ 完全持久化（数据库表 + 缓存）
- **扩展方式**：UI / API / LLM 即时增删，无需改代码或重启

## 3. 当前 DB 中的实际算子示例

SQL

```
-- 查询 V3 seed 初始化的唯一行
SELECT code, name, parameter_names, enabled FROM qc_operator_template;
-- 结果：ageConsistent | 出生日期与年龄一致 | ["birthDateField","refDateField","ageField"] | true
```

**body_dsl 定义：**

JSON

```
{
  "op": "eq",
  "field": {"$ref": "ageField"},
  "rhs": {
    "op": "ageYears",
    "birthDate": {"$ref": "birthDateField"},
    "refDate": {"$ref": "refDateField"}
  }
}
```

**规则中的调用方式：**

JSON

```
{
  "op": "custom",
  "code": "ageConsistent",
  "args": {
    "birthDateField": "birthDate",
    "refDateField": "admissionDate",
    "ageField": "age"
  }
}
```

> **执行逻辑**：`RuleEvaluator` 的 `case "custom"` 会取出 `body_dsl`，递归将 `{"$ref":"ageField"}` 替换为实际字段名 `"age"`，再交由 `evalBool` 运行展开后的标准 DSL。

## 4. 核心设计哲学：为什么内置算子不持久化？

1. **语义安全性**：内置算子白名单是 DSL 语言的核心定义。为了防止数据库被非法篡改后导致 DSL 语义漂移或注入攻击，核心算子必须经过代码审查。
2. **分散审查（Intentional Friction）**：新增内置算子必须修改 Evaluator、Validator 和测试用例。这种“故意为之”的设计确保了 DSL 解释器的关键部分是不可在运行时随意修改的，从而保证生产环境的稳健性。
3. **宏定义 vs 语言核心**：自定义算子本质上是内置算子的“宏组合”，其表达力不会超过内置算子集，因此在 DB 中动态增删是安全的。

## 8. 关于“内置算子动态化”的 Q&A

### Q: 是否建议将内置算子也实现动态化（热插拔）？

**A: 不建议。** 理由如下：

1. **痛点误区**：目前多参数情况已经可以通过“自定义算子模板”实现热插拔和 LLM 自动生成，不需要修改内核代码。
2. **安全退步**：若将 `RuleDslValidator` 的白名单改为读库，将失去对 LLM 幻觉算子或注入攻击的防御能力。
3. **表达力瓶颈**：动态化元数据并不等同于动态化逻辑。除非引入像 GraalVM JS 这样的沙盒引擎（这会带来巨大的维护负债），否则新逻辑依然需要 Java 实现。

### 推荐的优化路径（高 ROI）：

1. **补齐通用内置算子集**：一次性添加 `stringContains`、`regexMatch`、`inSet`、`between`、`yearOf` 等。这些通用算子能覆盖 95% 的业务场景。
2. **强化 LLM 抽离机制**：在 Prompt 中明确鼓励 LLM 将重复出现的复杂逻辑抽离为 `operators[]`（自定义模板），从而在不改代码的前提下丰富算子库。
